# Local Build Failures

Use this reference when `skills/sub2api-deployment/scripts/build-candidate.sh` fails or becomes unexpectedly slow. The release rule remains unchanged: fix local build or local cache problems on the Mac; do not compile on the production server.

## Docker registry mirror EOF

Observed errors:

```text
failed to do request: Head "https://mirror.ccs.tencentyun.com/v2/docker/dockerfile/manifests/1.7?ns=docker.io": EOF
failed to do request: Head "https://mirror.ccs.tencentyun.com/v2/library/alpine/manifests/3.21?ns=docker.io": EOF
failed to resolve source metadata for docker.io/docker/dockerfile:1.7
```

Meaning: Docker Desktop is using configured registry mirrors and BuildKit still performs metadata `HEAD` requests even when related tags appear locally cached.

Fix:

1. Avoid the remote Dockerfile frontend fetch by building from the temporary no-syntax Dockerfile generated by the project script.
2. Pull production bases with `--platform linux/amd64`.
3. Use an explicit registry domain for base images when Docker Desktop's configured mirrors are unreliable.
3. Re-run `build-candidate.sh`; do not switch to server-side build.

The project script now defaults production base images to `docker.m.daocloud.io/library/...` and warms them before `docker buildx build`:

```bash
docker pull --platform linux/amd64 docker.m.daocloud.io/library/node:24-alpine
docker pull --platform linux/amd64 docker.m.daocloud.io/library/golang:1.26.5-alpine
docker pull --platform linux/amd64 docker.m.daocloud.io/library/postgres:18-alpine
docker pull --platform linux/amd64 docker.m.daocloud.io/library/alpine:3.21
```

Override `PRODUCTION_BASE_IMAGE_REGISTRY` only after proving the replacement works with BuildKit metadata resolution, not only with `docker pull`.

If this repeatedly fails, inspect Docker Desktop registry mirrors with:

```bash
docker info --format '{{json .RegistryConfig.Mirrors}}'
```

Treat mirror failures as a local Docker/network issue, not a Sub2API code failure.

## Apple Silicon platform drift

Observed warning:

```text
WARNING: The requested image's platform (linux/amd64) does not match the detected host platform (linux/arm64/v8) and no specific platform was requested
```

Meaning: a tag such as `golang:1.26.5-alpine` may now point to the `linux/amd64` variant locally after warming production images. If Go verification uses that tag without `--platform`, Docker may run the test container through emulation or choose an unexpected architecture.

Fix:

1. Keep `PLATFORM=linux/amd64` for the production candidate.
2. Keep `GO_TEST_PLATFORM` separate; default it to the Docker host platform.
3. Verify the candidate image architecture after build with `docker image inspect`.

Do not merge test and production platform variables.

## Corrupted Go cache

Observed errors:

```text
pattern is/*: no matching files found
no required module provides package github.com/go-playground/locales
open /go/pkg/mod/golang.org/x/text@.../identifier.go: no such file or directory
chdir /go/pkg/mod/golang.org/x/sys@.../unix: no such file or directory
```

Meaning: the mounted Go module cache is partially downloaded or otherwise corrupted. The source tree and `go.mod` are not necessarily wrong.

Fix:

1. Stop the active test/build container.
2. Move the bad cache aside instead of deleting it if auditability matters.
3. Create fresh cache directories.
4. Re-run `build-candidate.sh`.

Example:

```bash
ts="$(date +%Y%m%d%H%M%S)"
mkdir -p /tmp/sub2api-go-cache-quarantine
mv /tmp/sub2api-go-cache/mod "/tmp/sub2api-go-cache-quarantine/mod-$ts"
mv /tmp/sub2api-go-cache/build "/tmp/sub2api-go-cache-quarantine/build-$ts"
mkdir -p /tmp/sub2api-go-cache/mod /tmp/sub2api-go-cache/build
```

If destructive cleanup is acceptable for a disposable cache, use the same intent carefully; never clean project source, database volumes, Redis, or remote production data as part of this fix.

## Slow or silent `go mod download`

Observed state:

```text
sh -lc /usr/local/go/bin/go mod download && /usr/local/go/bin/go test ...
```

with low CPU and no test output for minutes.

Meaning: the test container is waiting on module download or checksum lookup, often because it lacks the intended Go proxy environment.

Fix:

1. Pass `GOPROXY` and `GOSUMDB` into the test container.
2. Default to the same proxy policy as the Dockerfile build unless a task explicitly overrides it.

The project script now defaults to:

```bash
GO_TEST_GOPROXY=https://goproxy.cn,direct
GO_TEST_GOSUMDB=sum.golang.google.cn
```

If the process is instead high CPU with `compile`, `vet`, or `link`, it is probably cold-cache compilation, not a network hang.

## SSE scanner timeout hang

Observed behavior: targeted streaming timeout tests appear silent or stuck after an attempted fix that closes `resp.Body` and then drains `events` with `for ev := range events`.

Meaning: synchronously draining the scanner channel can deadlock after closing the upstream body, depending on scanner state and pending processed acknowledgements.

Fix:

1. Close `resp.Body`.
2. Return the first-output or first-token timeout error immediately.
3. Let the function's existing deferred cleanup release the scanner goroutine.

Do this for pre-output idle timeout, first-output timeout, and legacy first-token watchdog branches. Re-run:

```bash
go test -v ./internal/service -run '^TestOpenAIStreamingTimeout$' -count=1 -timeout=30s
go test -v ./internal/service -run '^(TestOpenAIStreamingTimeout|TestOpenAIStreamingFirstTokenDeadlineReturnsFailoverBeforeOutput)' -count=1 -timeout=60s
```

## Production guardrail

When local build errors happen, do not compensate by building on `43.136.113.101` or any 4 GB production host. First prove the old service is healthy, then upload only an already verified candidate archive. If `/health`, `/admin/ops`, SSH banner exchange, PostgreSQL, or Redis are unhealthy, recover the existing service before uploading or loading any image.
