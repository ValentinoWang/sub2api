解决你使用codex或者claudecode的最后一公里

客户端接入与排障更新于 2026.09.06
ERR-001模型不可见Codex 桌面历史案例：macOS

GPT-6 已接入，为什么 Codex 仍然看不见？

情况说明

你已经按照本站接入说明配置了 Codex，站点也已提供 GPT-6-Astra，但打开桌面应用后，模型选择器里仍然只有旧模型。也可能已经出现 GPT-6，重新打开原来的任务时却还是 5.6；或者终端里的 Codex 已经更新，桌面应用的模型列表却没有变化。

这几种表现很像“中转站还没同步新模型”，但并不一定是站点故障。中转站能否调用模型、桌面应用是否展示模型、当前任务实际选择哪个模型，是不同的环节。修复其中一个，不代表另外两个会自动更新。

本文适合这些情况：

  • 接入本站后，Codex 桌面模型列表没有 GPT-6-Astra。
  • 终端显示已经升级，桌面仍显示旧列表。
  • 模型已出现在列表中，但当前任务仍使用之前选择的模型。
  • 你不确定 Codex 连接的是本站、旧地址，还是本机代理。

如果你遇到的是登录失败、余额不足、明确的 401/403/429、持续超时或 5xx，请让 Codex 同时判断认证、权限、额度和服务状态，不要只按“升级客户端”处理。本文的历史修复在 macOS Codex 桌面上验证；Claude Code 的安装、配置与模型选择方式不同，不能直接照搬版本号和路径。

处理提示词与详细解答

Codex 帮你处理

给人看的：原因、证据与经验

1. 为什么站点支持了，桌面却不显示？

一次正常使用至少经过三个判断。“支持”“可见”“选中”并不是同一个开关。

检查层 它决定什么 你可能看到的现象
中转站与个人访问权限 你的接入入口和 API Key 能否请求目标模型 站点介绍有模型，但自己的目录或请求仍可能受权限、路由或服务状态影响
客户端模型目录 当前桌面版本把哪些模型放进选择器 API 请求成功，桌面仍不显示新模型
默认配置与任务选择 这一次任务实际请求哪个模型 新模型已经可选，原任务仍显示旧模型

因此，只在站点看到模型名称，还不能证明你自己的 Key 已经调用成功；只调用成功一次，也不能证明桌面选择器已更新。反过来，桌面没有新模型，也不能直接推出中转站不支持它。

在 2026-09-06 的历史案例中，中转服务的最小请求能够完成，阻碍可见性的环节在旧桌面引擎：它把 Astra 隐藏了。同时，默认配置仍显式选择旧模型。这解释了为什么既需要检查桌面版本，也需要检查配置和任务选择。

2. 为什么更新终端 Codex 没有效果？

桌面应用和终端命令可以各自携带一份 Codex。你在终端执行的 codex --version，通常说明的是当前命令路径找到的那份程序，不自动代表桌面应用正在使用的引擎版本。

这就会出现：终端已经更新，桌面仍调用旧引擎；或者电脑上安装了多个副本，更新了其中一个，实际打开的却是另一个。检查应从“正在运行的应用”出发，而不是只看安装命令是否成功。

历史案例中的检查对象 观察结果 对排障的意义
终端 Codex 已更新到 0.153.4 不能据此认定桌面完成升级
桌面内置 Codex 0.153.3 Astra 的目录标记为 hide 目标模型未在桌面列表正常展示
桌面内置 Codex 0.153.4 目录为 list，运行时返回 hidden=false 新引擎恢复模型可见性

这些是带日期的历史观测，不是让你永久安装某个旧版本。现在处理时，应优先检查官方当前支持的桌面版本，以及正在运行的进程是否确实使用了新引擎。

普通使用者不需要手动替换应用包内部的二进制文件。优先通过桌面应用提供的更新入口或官方完整安装包升级；“安装包已经下载”与“重启后正在运行新版”仍是两件事。

3. 为什么选了远端中转站，实际却可能走了别的地址？

Codex 的模型名称与连接地址是两个配置项。模型填对了，但连接到旧中转站或错误的本机端口，仍然可能得到旧模型目录、认证错误或连接失败。

你需要核对的是实际生效的 Base URL，而不只是配置文件里某一段看起来正确的地址。主配置、命名配置、启动参数以及已有任务的设置，都可能影响最终结果；具体优先级应按当前客户端检查。

  • Base URL：应符合本站给你的接入说明。路径可能已经包含协议前缀，不要凭印象重复添加 /v1。
  • provider 名称：它通常是本地配置中的标识，不是站点域名。不要把别人案例里的名称直接当作本站标准配置。
  • localhost / 127.0.0.1：表示你的电脑本身。如果没有本地转发服务，却把这里当成远端站点，就无法到达预期入口；如果你本来就使用本机代理，它也可能是有意且正确的配置。
  • 旧配置引用：重命名或移除 provider 后，命名配置和启动入口仍可能引用旧名字。让 Codex 检查引用关系，不要为省事删除所有 provider。

不要将整份用户配置替换成网上几行“能跑”的示例。这样可能丢失其他项目、MCP、记忆功能和可信目录设置。只改与当前故障有关的字段，并保留可恢复的备份。

4. 为什么仍显示 5.6，不一定是服务器回退？

如果默认配置从一开始就选择了 5.6，或者你打开的是之前使用 5.6 的任务，那么界面继续显示旧模型，首先说明的是客户端选择状态，而不是服务器偷偷把 GPT-6 换掉。

先确认桌面列表里能找到目标模型，再检查该任务的选择。更新默认配置后，可以新建一个普通任务，明确选中 GPT-6-Astra，执行一个很短的请求作为对照。不要把删除旧任务当作刷新模型的步骤。

如果界面显示 GPT-6，但你仍怀疑实际请求被改写，应收集客户端请求目标、响应中的模型字段、请求标识和报错时间，由站点管理员结合服务日志判断。模型在对话里自称是谁，不是可靠的模型身份检测方法。 返回的模型字段也只能作为链路线索，不能单独证明上游身份。

5. 要不要清理 models_cache.json？

不要把清缓存作为第一步。先确定当前版本从哪里读取模型元数据，再判断是否真的存在陈旧数据。

models_cache.json 属于模型元数据，不是你选择 provider 和默认模型的配置文件。历史案例中，旧引擎自带的模型目录已经把 Astra 标成 hide，所以即使删掉外部缓存，也不能让那份旧引擎自动获得新版目录规则。

对象 作用 这个问题下的处理边界
模型元数据缓存 保存客户端可用的模型描述或目录信息 先检查是否存在、是否被读取、是否过时；确认相关后才定点清理
config.toml 等客户端配置 决定入口、默认模型及其他功能 只调整相关字段，不能作为缓存删除
本地 memories 与任务历史 保存长期工作上下文与对话记录 模型不可见不是删除它们的理由
中转站 Redis / Docker 数据 属于服务端运行状态或存储 普通使用者不需要也不应为此清理

找不到缓存文件，本身不等于安装损坏。有些版本或运行方式可能使用内置目录；是否会生成缓存、何时更新，需要按实际版本验证。不要反复重启或反复删除，只为等一个文件出现。

确实需要清理时，应先明确准确路径、可恢复方式和清理后的验证动作。最终检查的是模型目录与实际调用是否恢复，不是文件有没有被成功删除。

6. 怎样升级，才不容易把当前任务打断？

如果你正在让 Codex 帮你更新 Codex 自己，更新的对象也可能是当前任务和本地工具所依赖的运行环境。直接在应用运行时移动、覆盖安装目录，可能导致旧进程继续运行却读取到新资源。

可以按下面的顺序处理：

  1. 先定位问题并准备更新来源、候选安装包或官方更新流程，保留必要的恢复信息。
  2. 保存当前工作，结束正在生成的回复和未完成的工具调用。需要退出应用时，不要让同一个活跃任务继续承担最后一步安装。
  3. 通过官方流程完成更新，再重新打开应用，核对实际运行版本和模型列表。
  4. 明确选择目标模型，用新任务做最小验证，最后再继续原来的工作。

切换 API provider 与升级桌面应用不是同一件事。本地历史和记忆可以继续保留，但不能承诺正在传输的连接和未完成工具调用无缝迁移。普通本站使用者无需为了客户端升级再部署一个本地 Sub2API，更无需重建本站容器。

7. 怎样确认自己的问题已经解决？

下面四项应分别检查，不要只凭一个绿灯判断全部正常。

  • 客户端正确：重新打开后，实际运行的是预期安装位置和版本，不是旧副本。
  • 模型可见：Codex 桌面的模型列表中可以找到 GPT-6-Astra。
  • 任务选中：当前任务或用于验证的新任务明确选择目标模型，不只是配置文件写了目标名称。
  • 请求完成：使用你自己的本站入口与认证完成一个简短请求，没有认证、权限或服务错误。

如果前三项通过、第四项失败，问题应继续沿 API 错误检查；如果 API 已成功而桌面仍不可见，重点仍在客户端目录与版本。一个短请求成功只证明最小链路，不代表长对话、全部插件、MCP 或工具调用都已验证。

8. 仍未恢复时，应该查哪里、联系谁？

结果或报错 优先核对 何时联系站点管理员
API 能调用，桌面没有模型 桌面实际版本、客户端目录、是否启动旧副本 本机检查后仍有入口或兼容性疑问时，附脱敏结果
目录没有目标模型，或提示模型不可用 目标模型 ID、个人 Key 权限、本站提供的实际入口 需要确认个人访问范围、模型映射或站点支持状态时
401 / 403 Key 是否失效、是否发往正确地址、权限是否允许 排除地址错误后仍拒绝访问；不要公开提交 Key
404 Base URL、接口路径及协议是否符合本站说明 路径核对无误仍不存在该接口
429 返回内容是否指向限流、额度或并发限制 降低并发后仍发生，或需要确认账号限制
超时 / 5xx 本机网络、代理、发生时间及站点公告 持续复现，或需要关联服务端请求日志

这些是排查方向，不是仅凭状态码就能确定的根因。网关和上游可能返回相似的状态；保留脱敏错误正文和请求标识比反复重装更有帮助。

联系管理员时，提供：系统与客户端版本、使用桌面还是终端、目标模型名称、发生时间及时区、做过哪些检查、脱敏后的错误内容，以及响应提供的 request ID。截图应遮住 API Key、认证头、邮箱、订单信息和私人对话；URL 中如包含凭证或令牌也应遮盖。

不要发送完整认证文件、整份配置目录或全部聊天记录。没有 request ID 时说明没有取得即可，不要猜测。管理员需要的是可以定位一次失败的最少信息，不是你的全部工作环境。
