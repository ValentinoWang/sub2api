# 链动小铺销售渠道：人工验收清单

这份清单只用于验收负责人确认用户可见的购买、发码和兑换体验。自动化测试、配置、任务执行和技术证据不属于本清单。

## 当前能验收什么

首期只验收这条实际流程：

```text
链动小铺商品付款 → 收到兑换码 → 在 Sub2API 兑换 → 余额到账
```

这不是支付宝或微信支付接入。验收通过后，只能说“链动小铺卡密销售渠道可用”。

## 开始前

验收负责人不需要查代码、运行命令、查看凭证或阅读技术日志。开始本清单前，需要拿到一个可购买的测试商品、一个 Sub2API 测试账号，以及本次商品在 `/admin/tools/ldxp` 中已经保存的映射记录。映射记录至少包含链动商品 ID、销售价和 Sub2API 入账余额。

技术负责人没有确认系统准备完成时，本人工清单不开始。

## 首期卡密渠道验收步骤

### 1. 按已保存映射核对商品

- [ ] 打开 `/admin/tools/ldxp`，在“连接与商品映射”表中找到本次已保存且已启用的商品行，记录该行的链动商品 ID、销售价和 Sub2API 入账余额。尚未保存的输入内容不能作为验收基准。
- [ ] 点击“同步远程商品”，在“远程商品”表中用商品名称找到待测商品；核对这一行的链动商品 ID 与已保存映射完全相同，并且映射状态为“已映射”。商品名称只用于定位和记录商品，不能用于推断到账额度。
- [ ] 核对“远程商品”表、链动小铺商品页和结算页的实际售价都与同一 `goods_id` 映射中的销售价一致。
- [ ] 商品说明明确告诉用户：购买后会得到 Sub2API 兑换码，以及兑换入口在哪里。
- [ ] 如果商品说明展示到账额度，该额度与同一 `goods_id` 映射中的 Sub2API 入账余额一致；商品说明没有展示冲突的套餐、额度或有效期。

### 2. 买一次

- [ ] 使用测试账号完成一次真实或沙箱购买。
- [ ] 链动小铺显示付款成功。
- [ ] 链动小铺发出一个兑换码，订单页面可以再次找到这次订单和发码结果。
- [ ] 兑换码没有被截断、缺字或混入其他文字。

### 3. 兑一次

- [ ] 兑换前记录测试账号当前显示的余额。
- [ ] 打开 Sub2API 的兑换页面，输入刚收到的兑换码。
- [ ] 页面提示兑换成功。
- [ ] 记录兑换后的余额，计算“兑换后余额减兑换前余额”。
- [ ] 余额增加值与第 1 步相同 `goods_id` 映射中的 Sub2API 入账余额一致。商品名称、销售价和商品说明不能替代这个额度基准。
- [ ] 退出后重新登录，余额和本次增加值仍然正确。

### 4. 再兑一次

- [ ] 再次输入同一个兑换码。
- [ ] 页面明确提示该码已经使用或不能重复使用。
- [ ] 账户余额没有再次增加。

### 5. 看库存

- [ ] 购买前后，链动小铺的可售数量变化符合这次购买。
- [ ] 已记录的补货数量与链动小铺实际增加的数量一致。
- [ ] 如果数量不一致，必须在验收记录中写明原因和处理人，不能直接判通过。

### 6. 做一次异常体验

- [ ] 在网络中断、页面刷新或重复点击的情况下，用户不会得到两次余额。
- [ ] 如果兑换页面提示失败，恢复网络后可以再次尝试；成功后仍只到账一次。
- [ ] 用户能看懂失败提示，并知道应该联系谁处理。

## 人工通过标准

下面每一项都满足，人工验收才算通过：

- [ ] 商品的 `goods_id` 与已保存启用映射完全相同，实际售价与映射销售价一致，商品说明包含兑换码及兑换入口且没有冲突信息。
- [ ] 付款成功后确实收到兑换码。
- [ ] 兑换码能在 Sub2API 使用，余额增加值与同一 `goods_id` 映射中的 Sub2API 入账余额一致。
- [ ] 同一个兑换码第二次使用不会再次增加余额。
- [ ] 购买前后库存变化合理，差异有明确解释。
- [ ] 普通用户不会看到管理功能或商户密钥。
- [ ] 页面没有把链动小铺说成支付宝、微信或 Sub2API 原生支付。

## LDXP 原生支付目前不验收

目前没有经过确认的 LDXP 服务端支付协议，因此本次人工验收不测试“Sub2API 页面直接使用 LDXP 收款”。技术人员也不得用浏览器现象或一张支付结果页证明原生支付已经接入。

只有在 LDXP 提供正式的服务端收款、回调、查单、退款和对账材料，并完成独立技术测试后，才另开一份原生支付验收，不与本清单混用。
