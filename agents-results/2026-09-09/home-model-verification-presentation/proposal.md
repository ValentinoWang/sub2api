# rest2build 首页模型实测与报告展示提案

日期：2026-09-09

文档性质：内容与展示方案，供后续确认；不属于已批准的开发 SSOT。

本次范围：标题、文案、报告卡片、经验文章和外部来源的展示关系。

事实状态：本次没有调用本站模型进行检测，没有新增本站检测结论，没有修改前端或发布内容。

## 1. 结论与展示顺序

采用用户提出的顺序：醒目标题 → 具体测试结果摘要 → 报告卡片 → 经验分享文章 → 第三方工具与来源链接。

首页负责传达服务承诺和展示有依据的摘要。经验文章负责说明测试对象、方法、结果和限制，外部链接提供工具入口或原始报告。用户不需要先阅读一篇检测原理介绍，才能找到本站的态度和报告。

测试尚未完成时，也可以先准备标题、文章与卡片结构。对外内容必须使用实际状态，“已通过某项测试”在对应报告存在且经过核对后才展示。

该模块针对本站 API 模型接入服务。账号订阅充值、权益到账和售后说明继续归属充值业务，不由模型检测报告替代证明。

## 2. 醒目标题与措辞判断

用户提出的候选标题：

> 确保 100% 正品，欢迎来测。

这个标题直接、醒目，但“确保 100%”会被理解为覆盖所有模型、分组和请求的绝对保证。现有黑盒测试只能为特定时间、配置和样本提供证据；后续即使多个工具全部通过，也不能直接推出所有请求永远真实的结论。因此，不建议把这句话作为由检测报告认证的结论发布，或用小字限制来抵消主标题的绝对承诺。

建议将经营承诺与检测事实分层表达：

| 用途 | 建议文案 | 使用条件 |
| --- | --- | --- |
| 醒目的服务承诺，推荐候选 | **标称什么模型，就交付什么模型。** / **欢迎来测。** | 运营方确认并实际履行如实标注、按约定交付的承诺；不能标成第三方已认证 |
| 尚未确认服务承诺时的中性标题 | **模型表现，欢迎来测。** | 配套检测方法与工具入口已可访问 |
| 有实际结果后的事实摘要 | **【模型 / 分组】已通过【工具名称】的【具体检测项】。** | 存在可追溯报告，摘要与报告范围一致，没有隐藏影响结论的异常项 |
| 不采用的证据推论 | “通过多个测试，所以全站 100% 原厂认证” | 工具通过结果不支持这一推论 |

这里的“如实交付”建议解释为：如实标注模型和服务分组，不用其他模型冒充标称模型；如某服务允许替代模型或降级，应在使用前清楚说明并取得用户选择。不同合法接入渠道本身不等于模型造假，API 兼容也不等于模型厂商授权。

本提案保留用户原句作为候选记录，不把它写成已经确认的公开承诺。推荐标题的服务承诺与本站是否已有检测报告是两件事。

## 3. 首页位置和信息层级

保留 `rest2build` 为首页主标题，保留现有品牌口号。首屏主标语附近增加简短的“欢迎来测”说明及入口；报告展示区域紧接首屏，位于经验卡片列表之前。

| 层级 | 内容 | 展示方式 |
| --- | --- | --- |
| 第一层 | 服务承诺标题、欢迎来测 | 作为该模块最醒目的文字，独立成行 |
| 第二层 | 已有报告的具体结论，或“本站专项报告筹备中” | 明确状态，不能仅用颜色表达 |
| 第三层 | 模型一致性、接口功能、响应表现的报告入口 | 桌面最多三列，手机单列 |
| 第四层 | “查看全部实测经验”“查看检测方法” | 进入本站经验中心；有内容后才提供入口 |
| 第五层 | 简短的检测范围说明 | 正常可读字号，与报告入口放在同一区域 |

模块使用整行背景或分隔线，保持与经验中心一致。卡片只用于独立报告，圆角不超过 8px；不将整段介绍再放进大卡片。浅色模式以清晰文字、青绿重点色和细边框为主；深色模式提高正文与背景对比度。通过用绿色，异常用橙红色，未测试或结论不足用中性色，并配套文字标签。

不使用官方认证印章、第三方盾牌徽章或工具 Logo 阵列暗示合作背书。工具名称采用普通文字引用；外部资源入口使用现有图标库中的外链图标。

移动端首屏至少保留标题和检测入口，报告卡片可以向下延伸。卡片标题、模型名与服务分组允许自然换行，不用横向滚动隐藏关键信息。

## 4. 测试前后的文案样稿

### 4.1 测试筹备阶段

以下样稿以运营方确认第 2 节的服务承诺为前提，否则使用“模型表现，欢迎来测”。

> **标称什么模型，就交付什么模型。**
>
> **欢迎来测。**
>
> 从模型一致性、接口功能到响应表现，查看检测方法，核对实际使用的服务。
>
> 本站专项报告筹备中，完成后按模型和服务分组公开。
>
> 查看检测方法 · 选择第三方工具
>
> 检测结果对应具体模型、配置与测试时间，不代表模型厂商认证。运行测试可能消耗 API 额度。

“完成后公开”只有在运营方确实准备开展和公开测试时采用。方法文章尚未上线时，这份样稿只存在于内容提案中，不创建空链接、不用禁用按钮伪装可用功能，也不展示“已通过 XX”等占位文字。

### 4.2 第一份报告发布后

标题保持一致，状态摘要由实际报告提供：

> **【模型名称】 · 【服务分组】**
>
> 【工具名称】 / 【检测范围】
>
> 结论：【报告结论】
>
> 测试时间：【时间与时区】 · 有效样本：【实际数量】
>
> 查看完整实测报告

以上方括号都是本文档的占位符，不是本站已有成绩。公开页面只渲染已经填写并核对的数据，不填示意分数、虚构日期或默认通过状态。

如果某工具只有分数或启发式判断，应按原口径显示“工具评分”或“未发现指定异常”，不擅自转换成“身份认证通过”。有异常时，摘要必须让用户看到异常范围，不能仅摘取其中的通过项。

### 4.3 有多份报告后

首页最多显示三张近期且具有代表性的报告卡片，并提供全部报告入口。按检测维度、模型覆盖和时间选择摘要，不按分数高低筛选；仍有效且影响用户选择的异常需要在首页摘要中可见。

不将多个工具的不同分数简单平均成“综合纯度”。每张卡片保留自身方法、对象和时间。

## 5. 报告卡片与状态

建议的三类报告：

| 报告类别 | 卡片回答的问题 | 摘要中需要明确的边界 |
| --- | --- | --- |
| 模型一致性 | 返回特征与标称模型或对照基准是否一致？ | 基准来源、模型版本、结论是否充分 |
| 接口功能 | 工具调用、流式响应、上下文和参数是否按预期工作？ | 具体接口与实际检测项目，不扩大到全部能力 |
| 响应表现 | 首字等待、输出速度与成功率是什么水平？ | 测量位置、时间窗口、样本量和请求配置 |

一张卡片包含：报告标题、模型、服务分组、工具或方法、结论、测试时间、样本量、完整报告入口。公开第三方原始报告存在时，可标明“附第三方报告”；只有工具主页时，只写“附检测工具链接”。

状态建议如下：

| 状态 | 公开表达 | 报告入口 |
| --- | --- | --- |
| 未开始 | 测试筹备中 | 只能进入已存在的方法文章，不叫“查看检测报告” |
| 已执行、尚未整理 | 报告整理中 | 不显示通过标识；可继续提供方法文章 |
| 有范围明确的通过结论 | 已通过指定检测项 | 必须能查看报告与范围 |
| 有异常或差异 | 发现差异 / 存在异常 | 展示异常明细、影响及后续说明 |
| 样本或基准不足 | 暂无充分结论 | 说明缺少什么，不算通过 |
| 配置或上游变化 | 需要复测 | 保留历史报告与原日期，撤下当前有效通过摘要 |
| 原报告无法核实 | 原报告暂不可核实 | 保留已有可信历史记录，不继续作当前背书 |

“已通过”不得仅依据工具名称、平台收录、付费推荐、截图中的绿色分数或一次接口连通。

## 6. 点击路径与经验中心组织

首页报告卡片主要链接到本站对应的经验文章，让用户先看到测试范围与解释，再按需打开外部来源。第三方工具入口可以出现在方法文章中，不要求用户先注册本站才能阅读公开报告。

建议沿用现有经验中心的“模型与用量”分类，以“模型与接口实测”为系列；有足够内容后再考虑独立分类。卡片以一个主要文章链接实现，避免整卡链接中再嵌套多个链接。

| 页面 | 作用 | 拟议路径，尚未实现 |
| --- | --- | --- |
| 系列说明 | 检测能说明什么、工具怎么选、如何复现 | `/experiences/model-verification` |
| 单份报告 | 一个明确测试对象和批次的完整记录 | `/experiences/model-verification/<report-slug>` |
| 现有经验索引 | 浏览相关系列和其他排障经验 | `/experiences` |

报告路径固定，复测建立新报告，并相互链接说明前后差异。新报告不得覆盖旧报告的日期、成绩或证据。异常原因后续查清时，可在旧文追加带日期的更正说明。

## 7. 单份经验报告的内容模板

1. **结论摘要**：本次发现什么，哪些问题仍无法判断。
2. **测试对象**：模型标识、服务分组、接口类型、执行日期与时区。
3. **测试条件**：工具版本、对照基准、思考配置、输入输出范围、并发和缓存条件等实际相关信息。
4. **结果明细**：各项结果、有效与失败样本、不能执行的项目及原因；性能数据注明单位和统计口径。
5. **结果解释**：检测支持哪些结论，哪些差异还可能由配置、版本或协议转换造成。
6. **复现方式**：使用哪个工具、选择什么接口、关键配置是什么；只使用合成测试内容。
7. **来源与材料**：工具官网、开源项目、可公开访问的第三方原始报告、本站脱敏结果附件。
8. **更新记录**：复测、更正、配置变化和失效状态。

“本站使用第三方工具自测”和“第三方独立执行测试”需要明确区分。本站整理的文章不因为引用了第三方工具就变成独立鉴定。报告有专用测试分组时应明确披露，不能让其结论代表普通用户分组。

公开材料不包含 API Key、Token、账号资料或真实用户对话。第三方测试使用临时、低额度密钥，不把凭证放进网页链接；是否上传测试摘要与自动生成报告需要按工具实际行为说明。

## 8. 与现有功能的关系

当前首页毫秒数来自 `/health` 往返测量，应继续称为“本站访问延迟”。它不代表模型首字等待或生成速度。当前状态页的成功率和延迟分位数来自监控探测，需按实际探测口径展示，不直接当作模型真实性结论。

Codex 原生 Responses、Claude 原生 Messages 与 OpenAI Chat Completions 应分别记录接口检测结果。某工具支持选择 Claude 或 GPT 模型名，不等于它已经覆盖该模型的原生接口。

## 10. 后续推进建议

先确认服务承诺标题，再准备系列说明文章与报告样式；按模型、用户可购分组和接口分别开展测试，整理第一批有依据的文章后补齐首页摘要。后续报告更新与上游变化同步处理。

当前交付物是这份内容提案，不包含测试成绩、上线结果或人工验收记录。后续若进入开发，另行确定实施范围，并按项目 [acceptance 规则](../../../acceptance/README.md) 管理机器证据与人工验收；本报告不替代验收合同、清单或签署结果。
