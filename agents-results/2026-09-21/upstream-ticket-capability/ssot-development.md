## 2. 当前打票链路的问题

| 环节 | Sub2API 当前事实 | 修改方向 |
|---|---|---|
| 探测结果 | `fireOpenAICodexTicketProbe` 取得响应头即返回并关闭正文；入库检查 HTTP 200、长度、前缀 | 先暂存候选，确认协议成功完成后入库 |
| 有效期 | `CapturedAt=now`，`ExpiresAt=now+TTL` | 可解析签发时间时按签发年龄约束；重复票不续命 |
| 缓存 | 每账号、每模型一张；内存 `sync.Map` 与 `accounts.extra` | 有界多票池、持久拒绝记录与明确版本 |
| 保存失败 | 先写内存，数据库失败只记录日志 | 持久化成功后发布可用票；失败时明确阻塞 |
| 调度 | 每轮结束后默认等待 6 秒；按缺票账号×模型启动 goroutine | 按账号预算、退避、公平排队、并发上限及多实例互斥 |
| 冷却 | 当前 harvester 未执行按账号持久化 429 冷却／401、403 暂停 | 业务和探测反馈共同约束账号级采集 |
| 反馈 | 已有响应头透传、会话账号来源守卫；票池写入只出现在主动探测路径 | 补业务被动收票及 HTTP/SSE/WS 精准关联失效 |
| 观测 | 管理端已有模型、ready、remaining、blocked 摘要 | 增加预算、退避、认证暂停、协议结果及检查缺口 |

依据：`backend/internal/service/openai_codex_ticket.go`、`openai_codex_turn_state.go`、`openai_gateway_forward.go`、`openai_gateway_passthrough.go`、`openai_ws_forwarder_payload.go`。上述事实来自本次读取源码，不是一次真实上游能力测试。

## 3. 明确“打票成功”的判定

打票指：使用选定 OpenAI OAuth 账号，通过已配置的打票代理发送一个最小合成 Responses 请求，收集该账号、实际出站模型对应的 `x-codex-turn-state` 候选。

分别记录三个结果：

1. **探测完成**：HTTP 状态、流内结果分别记录；观察到明确协议成功终态，未截断、超时、失败或超出检查边界。HTTP 200、`[DONE]` 或收到头部候选本身均不足以证明成功。
2. **候选可复用**：满足本地格式、归属、年龄、拒绝历史和版本约束，并已持久化；只表示符合本地策略。
3. **带票请求完成**：后续同账号、同出站模型的业务请求实际完成，且观察到的协议反馈没有明确拒绝该票；作为运行证据单列。

292、312 是当前实现使用的长度标签，不是官方能力等级。不承诺请求必然获得 292，不把长度、可解析时间戳或一次成功等同于签名验证、服务端有效期或模型推理质量。用户能验收的是链路、状态转换、错误处理和真实请求结果。

## 4. 服务端方案

### D1：完整收票与失败分类（第一优先级）

- 保留专用打票 HTTP transport 与现有代理设置，继续按账号取 OAuth 凭据，不落入客户业务转发队列。
- 响应头候选暂存；增量检查 SSE/JSON 的协议字段，成功终态后提交。探测总正文默认不超过 4 MiB、单事件不超过 256 KiB、单次请求默认 15 秒，作为本地可调防护值。
- 解析分块 UTF-8、LF/CRLF、多行 SSE data 和结构化失败。超限、未知编码、断流、取消均记录检查缺口，不入库、不判成 312。
- 只读取协议约定的头、根级元数据、`client_metadata` 和 response 对应位置；不得递归扫描用户消息、工具参数、生成正文和任意 metadata。
- HTTP 200 中的配额失败记为“HTTP 200 + 协议配额错误”，同时进入冷却，保留两层事实。

主要文件：保留 `openai_codex_ticket.go` 作为调度/注入入口，提取 `openai_codex_ticket_probe.go` 与 `openai_codex_ticket_feedback.go`；参考 Codex_degrade 的 `src/fetch.rs`、`src/feedback.rs`、`src/request_history.rs`。

### D2：签发年龄、有界票池与持久化

- 桶键为服务器账号 ID、实际 OAuth 身份代次、实际出站模型。普通 access token 刷新且身份未变时不新建桶；更换实际 OAuth 主体时推进身份代次并停用旧身份票。模型映射和 compact 路由继续与现有调度使用同一解析结果，不能用客户端别名取票。
- 每桶最多 4 张，优先使用最新可注入票；库存为上限，不是补票目标。服务器总容量单独配置，不照搬桌面全部账号 128 张的常量。
- 可解析的 Fernet 签发时间只用于本地年龄过滤。默认 55 分钟进入补票、59 分钟停止注入、60 分钟淘汰；未来超过 30 秒的候选拒绝入库。签名与上游有效期仍未知。
- 同一票用指纹去重；重复收到不重置签发年龄、首次捕获时间和拒绝历史。旧请求与旧探测结果必须通过桶版本检查，不能覆盖新票。
- 通过现有 `SecretEncryptor` 加密设施保存原票，启用前要求配置跨重启稳定的加密密钥；禁止使用每次启动随机生成的密钥承诺恢复能力。解密失败保留记录并停止复用，不以重新初始化覆盖拒绝历史与预算。状态 API、审计与日志不返回完整票、OAuth 凭据、代理密码或业务正文。
- 新增票据／拒绝持久层及账号采集控制记录，使用 PostgreSQL 事务与条件更新。内存是缓存；Redis 可做唤醒、短租约或缓存，不能成为重启后预算、拒绝历史的唯一来源。
- 入库成功后才对请求发布；持久化失败停止新票复用并展示存储错误。当前 `accounts.extra` 中既有单票只迁移一次：重验格式、年龄、账号归属，保留原时间；无法解析的旧票作废，重新按预算获取。迁移完成移除旧双写实现。

主要文件：新增 ticket repository、schema/migration、pool service，调整 `account_repo.go` 的旧票读写及管理 DTO 脱敏；参考 `src/turn_state.rs`。

### D3：账号预算、退避与服务器调度

- 功能默认关闭；启用后只有启用且可调度的 OAuth 账号参与。每个账号初始限额为每小时 30 次，失败和取消也计入；这是建议本地成本上限，可配置，不是上游额度声明。
- 同账号所有模型和所有服务实例共用预算；派发前持久化预留。换代理、重启、手动刷新、新票或 312 都不重置预算；时钟回拨不能补充预算。
- 无收益退避依次为 30、60、120 秒，最多 600 秒。429 与结构化限流遵守 `Retry-After`／reset，较长等待不能被本地上限截短。
- 401/403 暂停该账号采集，手动刷新不解除。服务器恢复入口为凭据修复后的显式重新校验，或暂停之后发出的已完成业务请求；必须比较认证代次与时间。仅返回 HTTP 200、旧请求迟到成功不足以恢复。
- 使用持久租约和版本条件写，防止多实例重复打票、过期 worker 回写；整个部署默认 2 路，同账号默认 1 路，两项并发限制均通过数据库租约跨实例生效。账号之间公平排队，加入适量巡检抖动。
- 保留当前配置的 Astra、Sol 两个目标模型，不直接复制桌面的 Astra-only 策略。目标模型缺票时均可进入按账号共用预算的队列，临期/缺票优先，已有新鲜票不继续填满池。被动新增模型默认不扩大主动探测集合。
- 必须校验 `fail_closed` 与模型配置：被严格门控的模型必须存在取得首票的路径。认证暂停后的恢复也必须独立于“已有票业务才可成功”的前提，避免永久锁死。

主要文件：拆分 `openai_codex_ticket_harvester.go`、`openai_codex_ticket_control.go`，增加数据库原子预算与租约实现，连接服务生命周期；参考 `src/probe_control.rs` 与 `src/lib.rs` 的调度规则。

### D4：业务反馈与精准撤票

- HTTP、SSE、JSON、WS 统一保存内部关联：实际账号、实际模型、请求／响应标识、注入票指纹、桶版本、认证代次。
- 业务自然响应可被动提供候选；仍须通过归属、年龄、版本和失败判定，不额外发请求。主动探测与业务反馈共享同一个池。
- `response.status` 声明失败、不完整或取消时，同样禁止回收该响应候选；记录失败后，迟到的完成事件不能重新开放收票。候选指纹可留作关联证据。
- 312 或明确指向 `x-codex-turn-state` 的错误，只停用能明确关联的票。同一响应先给新票再拒绝时，能关联到新签发票；旧请求拒绝不能清掉新票。
- WS 并发无可关联 ID 的信号记为“未关联”；不猜测撤销。迟到响应关联保留有界窗口。
- `invalid_encrypted_content` 未指定该头时，不判为票据失效；普通 401/403/429、网络错误和 5xx 分别处理。
- 不因补票、312 或观察失败而重放用户业务请求。SSE/WS 正文原样转发，检查只使用有界副本，不改变当前连续会话与缓存路由行为。
- 所有注入路径统一覆盖：普通 Responses、passthrough、Messages 兼容、compact、WS。上游 API-key 账号不打 OAuth 票；客户端使用 Sub2API API Key 不等于上游账号是 API-key 模式。

主要文件：`openai_gateway_forward.go`、`openai_gateway_passthrough.go`、`openai_gateway_response_handling.go`、`openai_gateway_messages.go`、`openai_ws_forwarder_payload.go`、WS 事件处理路径及 `openai_codex_turn_state.go`。复用已有会话账号来源守卫。

### D5：最小管理界面与成本口径

沿用现有总开关和打票代理输入，仅补充：每模型可用票数、距停止注入的时间、最近探测结果、账号预算、退避／认证暂停原因、存储故障和检查缺口；手动刷新仍走同一门禁。

管理界面使用“候选可用、上次带票请求完成、已拒绝、检查不完整”等事实状态，删除把长度标签解释为模型质量保证的说法。票据池不会出现在客户普通账号数据导出中。

合成探测单独标记为运维消耗，不归入某个客户 API Key 的扣费；记录可获取的 usage 与采集请求数。上游可能计费或扣配额，未返回 usage 时记录未知，不计为零。频繁手动刷新不得绕过预算。

## 6. 必须覆盖的验收场景

| 场景 | 预期 |
|---|---|
| 200 + 头部 292 + 成功终态 | 可入库，记录真实协议结果 |
| 200 + 头部 292 + 流内失败／截断／取消／只有 DONE | 不入库，失败或检查不完整 |
| 原票重发、未来票、过期票、拒绝过的票 | 不延寿、不误恢复 |
| 两个账号、两个模型、模型别名及 compact | 只按实际账号及出站模型使用对应桶 |
| 并行请求、旧探测迟到、旧请求拒绝、WS 无 ID | 版本校验生效，不误删当前票 |
| 再启动、换代理、手动刷新、两服务实例同时抢预算 | 已用预算／退避／认证暂停保留；不重复预留和派发 |
| 数据库写失败、缺少稳定加密密钥或解密失败 | 不发布未持久票、不覆盖预算与拒绝记录，界面可解释 |
| 401/403 后修复凭据且无票 | 有受控恢复路径；不陷入缺票与认证暂停互相等待 |
| HTTP/SSE/WS 不同分块、编码和中途断开 | 原内容透传；检查缺口不伪造为“正常”或 312 |
| 功能关闭、非 OAuth 上游、非目标模型 | 不触发主动打票或跨模型注入；保持约定原链路 |
| 探测计费与普通请求 | 探测不误扣客户余额；真实上游成本未知时如实显示 |

## 8. 会话切换与恢复经验

以下经验来自用户在本任务中补充的既有排障记录。本轮没有重做该次 provider 切换、修改 Codex 会话或逐会话发送消息；这些历史结果不作为本次源码升级或打票功能的验证证据。

**会话能否继续使用，要同时看存储记录、运行状态和实际接口，不能只改 provider 字符串。**

1. **先确认目标服务，再修改。** `openai` 是具体的官方 provider，不是通用标签。若用户要继续使用第三方服务，修改前必须说明切换到 `openai` 会改变请求路由，并核对实际 provider 定义、目标地址及认证配置；不能仅按名称替换。
2. **文件、数据库、内存要一致。** 会话文件和 SQLite 索引更新后，已加载会话仍可能使用旧 provider，并将旧状态写回。用户提供的案例出现过索引重新变回 `openai`；因此必须将持久记录与运行中的会话状态一并核对。
3. **切换前先结束活动请求，再重新加载。** 用户提供的案例通过对已停止运行的异常会话暂时归档再恢复，成功卸载旧运行状态。该方法只适用于活动流式请求和工具调用已结束的会话，不能用归档中断在途工作；新 provider 也不保证延续旧 WebSocket 或工具续接。
4. **“修改成功”不等于“能发消息”。** 分层验证记录正确、旧状态已卸载、认证有效、实际模型请求成功。用户提供的案例最终验证到了第三方接口 HTTP 200 和 `OK`，但没有逐个向 19 个会话发送测试消息；只能报告接口结果与已核对的会话范围，不能宣称全部会话实测通过。
5. **按用户实际目标完成恢复。** 目标是原会话能够继续使用，不能在修正记录后把恢复任务入口留给用户。用户指出此前遗漏了 2 个为排障而归档的会话；今后应恢复本次排障临时归档的入口并核对可访问性，保留用户原本有意归档的会话状态。

固定处理顺序：**确认目标服务 → 备份 → 修正会话记录 → 安全卸载旧状态 → 验证接口 → 恢复任务入口**。备份只进入受限本地位置，记录中不得暴露凭据或完整对话内容。需要验证原会话时使用已有明确授权和范围，不能擅自批量向历史会话发送测试消息。

全局配置、记忆和对话历史必须保留：不以 provider 专用配置覆盖 `~/.codex/config.toml`，不删除其功能开关、记忆配置、provider 定义、profile 或项目可信配置。`~/.codex/memories/` 是 Codex 记忆，`~/.codex/sessions/` 与 `~/.codex/archived_sessions/` 是任务历史，Sub2API Redis 只负责服务侧 Responses/WS 粘性；重置 Redis 不能代替修复 Codex 会话状态。

本方案的打票改造继续复用当前服务和认证配置，不把切换 provider 作为打票修复步骤。若后续接入验证涉及 provider 切换，才应用本节流程，并单独记录每一层的验证结果。

尚待确认或运行验证的事项见 [openproblem.md](openproblem.md)。
